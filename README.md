Tips should be accepted through as many endpoints as possible. They are the passive counterpart to automatic billing for simple services. A tip is money sent because the sender wants to give it, with no offer, product, entitlement, or promise in return.

This section holds:

- `data/records/schema/tip-endpoint.schema.json` and the dated catalog
  `data/records/2026-09-05-tip-endpoints.json` — every endpoint the org can receive a tip
  through today, one row each (`id`, `rail`, `provider`, `walletId`, `state`,
  `verificationOperation`, `bookingAccount`, `feeSchedule`, `handsItem`). `walletId` is a
  `"<chain>:<address>"` identity resolved through `@red-cup-engineering/key-management-services-
  section`'s WalletRegistry, or `null` (2026-09-05 ruling, payment-receivers-are-parameters-
  never-literals: a catalog row never carries a literal receiver address/account/handle). A row
  with no matching registry wallet is `state: "needs-wallet"`, never an invented `walletId`.
- `scripts/derive-tips-page.mjs` — resolves every listed (`live`/`code-ready`) `walletId`-
  carrying row through `key-management-services-section`'s `resolvePaymentReceiver` at render
  time; a row whose wallet has no custody entry verified `"agreed"` is omitted from the rendered
  page and reported as a `refusals` row instead of ever being shown as a payable receiver.
- `scripts/verify-tip-receipt.mjs` — dispatches a claimed receipt to its rail's verification:
  an already-ingested Stripe `checkout.session.completed` event (via
  `@red-cup-engineering/stripe-engineering-services-section`'s own webhook journal) for `card`;
  `@red-cup-engineering/verify-hbd-payment-service`'s two-Hive-node agreement for `hive`; two
  independent Base public RPC endpoints agreeing on a USDC `Transfer` log for `base-usdc`. A rail
  with no wired verification refuses as data (`{verified: false, reason:
  "verification-not-implemented-for-rail"}`), never throws.
- `scripts/compute-tip-transaction.mjs` — the pure receipt-to-Beancount-directive transform
  (fabricated through the jsnode operation-package line; its work order is kept at
  `data/records/compute-tip-transaction-work-order.md`), using
  `@red-cup-engineering/computer-ledger-system-services-section`'s exact-decimal string
  arithmetic, never a float.
- `scripts/book-tip.mjs` — books one verified receipt: appends the directive (and any `open`
  directives its accounts still need) to a dated sidecar under this section's own
  `data/logs/ledgers/<date>-tip-transactions.beancount`, headed exactly like the Group's other
  generated sidecars ("Generated by scripts/book-tip.mjs (@red-cup-engineering/tips-engineering-services-section).
  Do not hand-edit.") so the books session can `include` or copy it into the main ledger's own
  `561-group-services-section/data/logs/ledgers/` directory. This operation never writes to the
  main ledger itself.
- `scripts/derive-tips-page.mjs` — the public tips-page Markdown fragment, listing only `live`
  and `code-ready` endpoints; a `needs-account` endpoint's `handsItem` comes back as a
  `handsItems` row instead, never onto the page.
- `apps/tips-cli.mjs` — the composed face (`verify`, `book`, `page`, `endpoints` subcommands).

## Stripe: a customer-chosen-amount tip offering

`@red-cup-engineering/stripe-engineering-services-section` 0.1.9 added a `general-tip` offering to its fixed
catalog (`content/config/offerings.json`), `mode: "payment"` with a `customerChosenAmount`
(`{minimum, maximum, preset}` in cents) instead of a fixed `unitAmount`. `buildCheckoutSessionForm`
emits Stripe's `custom_unit_amount` price-data fields
(`docs.stripe.com/payments/checkout/pay-what-you-want`, fetched 2026-09-05: `enabled`,
`minimum`, `maximum`, `preset`, quantity fixed at 1, mode `payment`, no other line items, no
discounts) instead of a fixed `unit_amount`. The offering is `status: "test-only"` until the
founder arms live Stripe credentials — the owner's Stripe fence is about product quality, not
tips, but this lot leaves activation to that separate decision. No product, entitlement, tax
position, or refund promise is created; the verified `checkout.session.completed` event
reconciles through the existing `ingestWebhook` verified-event path exactly as any other offering.

## Booking shape (coordinator note, 2026-09-05)

The Group's main ledger at `561-group-services-section/data/logs/ledgers/561-group-main-ledger.beancount`
includes its generated sidecars by glob (`2026-*-chain-balance-assertions.beancount`,
`2026-*-price-directives.beancount`, `2026-*-fixed-asset-registrations.beancount`,
`2026-*-inference-expense-transactions.beancount`). `book-tip.mjs`'s default output matches that
same sidecar shape (a headed, dated `.beancount` file with `open` and transaction directives) so
the books session can add it to that include list or copy it in; this section's own
`data/logs/ledgers/` is its own log, not yet the Group's books, and this section does not edit
the main ledger.

`Income:Tips:<Provider>` accounts are consistent with the main chart's existing `Income:*` open
accounts. Rail asset accounts reuse the main chart's existing conventions where one exists
(`Assets:Cash:Operating` for card/bank/platform rails, `Assets:Digital-Assets:Hive:Custody:<Account>`
for Hive, `Assets:Digital-Assets:EVM:Base:Tokens` for Base USDC) and `open` a new
`Assets:Digital-Assets:Lightning:Custody` and per-provider `Expenses:Fees:<Provider>` account
where the main chart does not yet have one, dated at first use so they merge without duplicate-open
errors.

## Fee schedules

Read from each provider's first-party page via WebFetch on 2026-09-05, cited with the exact URL
and date in each endpoint's `feeSchedule`. Where no first-party page could be reached (Ko-fi,
Hive Resource Credits, Cash App all returned 403/404 to this lot's fetches), `feeSchedule` is the
literal string `"unknown"` rather than a guessed figure.

## Dependencies

`@red-cup-engineering/computer-ledger-system-services-section` (exact-decimal arithmetic, via its
`src/decimal.mjs` subpath — the package declares no `exports` map restricting subpath imports),
`@red-cup-engineering/verify-hbd-payment-service` (Hive two-node verification),
`@red-cup-engineering/stripe-engineering-services-section` (the card rail's webhook journal),
`@red-cup-engineering/semiotic-eavt-engineering-services-section` (receipts).

## Out of scope for this lot

Lightning/ZBD verification code (the endpoint is `needs-account`; no ZBD merchant account exists
to verify against yet), and any change to `pool-service`, `energy-bank`, or files under the
finance operations or public financial sections — those are other lots' custody.
